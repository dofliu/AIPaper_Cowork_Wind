### 2.3 Farm A 的 `active_power` 一度抓成「可能發電量」

字典裡有兩個 kW 通道：

```
power_29   "Possible grid active power"   ← IEC 61400-26 的可用率術語，模型值
power_30   "Grid power"                    ← 實測
```

「Possible power」是「這台機在當下風速*本來能*發多少」，由風速和功率曲線算出，
**一台正在衰退的機組在它上面完全不留痕跡**——那正是我們要偵測的東西。

已改為實測通道優先；只剩能力值通道時拒絕解析並說明原因。
現用 `power_30_avg`。

### 2.4 主軸承通道有故障碼 — **Farm C 與 Farm B 都有**

Farm C 的 `sensor_194/195` 有超過 1% 的列固定是 850.0。與另外三個約 46 °C 的
通道平均後，主軸承溫度變成 **363 °C**。餵進 Mahalanobis 會產生巨大距離＝假警報，
且不報錯。

已在**逐通道**層級過濾（取平均之前），過濾政策與拒絕筆數記在
`scorer_summary_<farm>.json` 的 `range_filter`。修正後 p99 = 53.957。

**五個通道都是真的主軸承**，不要剔除：乾淨資料上跨組相關 0.945–0.948，
中位數 50.7 vs 46（內圈比外殼量測熱，物理正確），都遠高於環境溫度 28 °C。

**【2026-08-15 六趟評分器實跑後補充】這不是 Farm C 獨有的。**
Farm B 的主軸承對 `sensor_51/52`（signal map 取兩者平均）同樣有故障碼：

| 風場 | 通道 | 拒絕筆數 | 佔該場總列數 |
|---|---|---|---|
| B | `sensor_52_avg` | 4,012 | 0.47% |
| B | `sensor_51_avg` | 464 | 0.05% |
| C | `sensor_194_avg` | 67,896 | 2.13% |
| C | `sensor_195_avg` | 67,871 | 2.13% |

**兩場的失效型態不同，這點值得寫進手稿**：
Farm C 兩個通道幾乎同時失效（67,896 對 67,871，差 25 筆），像是共用同一條
擷取路徑；Farm B 的兩個通道**各自獨立失效**（4,012 對 464，差 8.6 倍）。

由此帶出一個必須揭露的細節：逐通道過濾是在取平均**之前**做的，所以當
`sensor_52` 被拒而 `sensor_51` 沒有時，那些列的 `main_bearing_temperature`
**是單一通道值，不是兩通道平均**。這是刻意的設計（一個壞通道不該連累另一個），
但它意味著那些列的特徵雜訊特性與其他列不同。Farm B 約 0.47% 的列屬於此類，
量級上可忽略，**但手稿不能寫成「一律取兩通道平均」**。

Farm A 沒有主軸承通道（2.2），而那正是三場中唯一帶故障碼的訊號——
所以 Farm A 的拒絕數為 0 是合理的，不是濾網沒作用
（已確認 `range_filter.enabled = true` 且五個範圍都載入）。

## 5. 這個專案最重要的一課

**到目前為止最嚴重的缺陷，沒有一個會報錯。**

它們全部照常跑完、照常輸出漂亮的數字，只是數字是錯的。而且**全部都是拿真實
資料實跑才撞到的，沒有一個是讀程式碼讀出來的**。

清單（給後續協作者當檢查清單用）：

| 缺陷 | 後果 |
|---|---|
| FAR 算在故障案例上 | 把真陽性當誤報，讓最好的偵測器看起來最差（0.3102） |
| score CSV 表頭 `wind_speed` 重複 | DictReader 只留後者；感測器掉線的列風速被讀成空 → 落錯分箱 → **偏誤核心主張** |
| `[FARM:]` 前綴用子字串比對 | `A:` 命中三個風場（`farm` 裡有 a），兩個風場用錯誤風速欄分箱 |
| 把「可能發電量」當實測功率 | 最有資訊量的特徵失去偵測衰退的能力 |
| 850.0 故障碼進特徵向量 | 巨大 Mahalanobis 距離＝假警報 |
| `scorer_summary.json` 固定檔名 | 三風場寫同一目錄，Farm C 蓋掉 A 和 B |
| 單位檢查器用比例比較攝氏 | 三個假警報。**會叫錯狼的檢查器比沒有更糟**——它訓練人忽略它 |
| 診斷工具預設只讀 8/58 個檔案 | 印「from 8 case file(s)」卻不說總數，把一角當全貌 |
| `median_lead_days` 只在有偵測到的案例上取中位數 | 漏檢離開母體而非計為漏檢 → **漏掉越多困難案例分數越好看**。dtaci 的「提前 33.44 天」是 6 取 1 |
| lead time 無下界 | 故障發生**之前**的誤報被計為提前預警，而且報得越早收割越多 |
| D1/D6 的 case 93 裁切只寫在設定檔註解裡 | 沒有任何程式套用它，也不會報錯——重疊視窗會照常進入正常案例的誤報統計 |

最後兩項合起來，讓一個評估器缺陷被誤判為方法缺陷，並以「主要限制條件」
呈報上去，**差一步就會導致動用已簽核參數去修一個量尺的錯**（見 6.1）。

**由此形成的工作準則**：

1. 每支工具都要有自己的行為測試。
2. 新測試要**反向驗證**——把修正還原，確認測試真的會失敗。只會 PASS 的測試是裝飾。
3. 檢查要能**兩個方向都失敗**。只往一邊失敗的檢查不是證據。
4. 取樣要說明涵蓋率。跨距取樣可能完整漏掉週期性異常（實際發生過：
   每 40 列注入、每 20 列取樣，完美錯開）。
5. 物理範圍、閘門門檻這類定義只能有**一份**。兩支工具對「什麼叫可能」意見不合，
   比其中一支寫錯更糟。
6. **任何要呈報為「方法限制」的負面結果，呈報前先在真值已知的合成資料上做一次
   歸因**，確認那個限制不是量尺造成的。`scripts/diagnose_earliness_gap.py`
   是這個流程的範例：先逐一重現被質疑的數字，再逐項排除候選解釋。
7. **統計量一律連同分母一起呈現。** 中位數、比率、平均，只要母體會隨方法變動，
   就必須把 n 印在旁邊。上表最後兩項都是分母被藏起來造成的。

### 6.1 ~~【最重要】非劣性未通過~~ → **已解除（2026-08-15, R22）**

**這一項先前是本文件的頭號風險，現已查明為評估指標的缺陷，不是方法的缺陷。**
`min_bin_samples` **維持 500，不需要重啟**。

原本的呈報是：本方法相對 static 損失約 8 天 lead time、超過 2 天邊際，
並詢問是否開放調整 `min_bin_samples`。`scripts/diagnose_earliness_gap.py`
把那組數字逐一重現後歸因，三個候選解釋兩個被排除：

| 假說 | 結論 | 依據 |
|---|---|---|
| 暖機（每箱緩衝填得慢） | **排除** | 首個可判定索引 530 對 pooled 500，僅差 0.2 天；故障最早在索引 3800 才爬升 |
| 工作點不對等 | **排除** | 各方法邊際誤報率都在名目 0.05 附近（0.045–0.059） |
| **故障前誤報被計為提前預警** | **成立，且是全部缺口** | static 的 16.53 天當中有 **6.11 天**來自故障開始前 880 步的告警；aci 為 8.28/18.70。本方法 0.00 天 |

兩者回報的數字都超過該 fixture 物理上可能的 10.42 天上限——
它們在「偵測」一個當時還不存在的故障。

**eval-v1.0 的兩個缺陷（都不報錯）已修正為 eval-v1.1：**

1. `median_lead_days` 只在有偵測到的案例上取中位數，漏檢直接離開母體
   → 漏掉越多困難案例分數越好看。dtaci 的「提前 33.44 天」是 6 取 1，
   w1acas 也是 6 取 1，本方法是 6 取 6，舊表格看不出來。
   現在一律附 `detection_rate` 與分母，並新增免參數的
   `median_lead_days_missed_as_zero`。
2. lead time 無下界 → 新增 `--detection-horizon-days`，**刻意不給預設值**。

**修正後，本方法在所有掃描門檻下非劣性皆通過**（12 案 fixture、對 static、
邊際 2 天）：未設限 −0.12／H=3 0.00／H=5 0.00／H=7 −0.40／H=10 −0.95／
H=14 −0.64（負值代表本方法反而更早）。偵測率 ours 6/6、static 6/6、
aci 4/6（設限後 1/6）、dtaci 1/6（設限後 0/6）、w1acas 1/6。

條件覆蓋率的主張不受影響，依然成立（最差分箱偏差 0.0061 對基線 0.1611–0.2387）。

**仍待劉老師裁決**：偵測門檻 H 是否納入評估協定、取值多少。這是**新增的評估
參數**，程式不預設。掃描實據見《[裁決請求] 2026-08-15 R22》：H 太小會截斷真實
提前量（H=3 時所有方法都被壓成 3.00），H 超過物理上限則故障前誤報又被放回來
（H=14 時 aci 從 1/6 回到 2/6），可用區間在兩者之間。

> 仍是合成資料。它證明的是「指標現在量到它名稱所指的東西」，
> **不是** CARE v6 的實驗結果。真實數字仍需本機的 score stream。

### 8.1 文件命名規範（2026-08-15 新增，起因見下）

**問題**：多位協作者（Gemini Spark、Codex B、排程自動化研究助理，加上不只一個
同時執行的 session）各自遞增版本號，於是同一個版本號被不同人用在不同文件上。
截至 2026-08-15 已發生 **6 組撞號**：v1.7、v1.8、v2.2、v2.4 各兩份，
v3.0 三份，v3.9 兩份。最嚴重的一次是 v4.0 已存在後又出現一份 v3.9，
**最新的紀錄反而掛著最舊的版號**。

**根因**：版本號是一個需要全域協調的計數器。並行寫入時它必然碰撞——
這不是誰粗心，是編號方式本身不適用於多寫入者。

**規範**：日誌與進度文件標題一律採

```
<文件類型> v<版號> — <YYYY-MM-DD HHMM> — <作者>
例：風能運維論文協作開發日誌 v4.1 — 2026-08-15 2211 — 排程自動化研究助理
```

- **時間戳是真正的識別碼**，版號只是給人讀的順序提示。
  時間戳天然唯一，不需要任何人協調。
- 撞號時**不改動歷史文件的版號**（其他文件會引用它），
  只補上時間戳與作者以資區別。
- 新建文件前**先看資料夾裡最大的版號**再遞增；不確定就直接用時間戳。

**判斷「哪一份最新」時，一律看時間戳，不要看版號。**

> 更根本的解法是別再用 Drive 追狀態：**現況以本文件為準，日誌只記流水帳**。
> 本文件在版控裡，天然有唯一的歷史與衝突處理，不會有這個問題。
