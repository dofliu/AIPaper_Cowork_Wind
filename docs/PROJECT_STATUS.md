### 2.3 Farm A 的 `active_power` 一度抓成「可能發電量」

字典裡有兩個 kW 通道：

```
power_29   "Possible grid active power"   ← IEC 61400-26 的可用率術語，模型值
power_30   "Grid power"                    ← 實測
```

「Possible power」是「這台機在當下風速*本來能*發多少」，由風速和功率曲線算出，
**一台正在衰退的機組在它上面完全不留痕跡**——那正是我們要偵測的東西。

已改為實測通道優先；只剩能力值通道時拒絕解析並說明原因。
現用 `power_30_avg`。

### 2.4 Farm C 主軸承有 850.0 故障碼

`sensor_194/195` 有超過 1% 的列固定是 850.0。與另外三個約 46 °C 的通道平均後，
主軸承溫度變成 **363 °C**。餵進 Mahalanobis 會產生巨大距離＝假警報，且不報錯。

已在**逐通道**層級過濾（取平均之前），過濾政策與拒絕筆數記在
`scorer_summary_<farm>.json` 的 `range_filter`。修正後 p99 = 53.957。

**五個通道都是真的主軸承**，不要剔除：乾淨資料上跨組相關 0.945–0.948，
中位數 50.7 vs 46（內圈比外殼量測熱，物理正確），都遠高於環境溫度 28 °C。

### 2.5 Farm C 的 `sensor_146/147` 已排除

四個候選轉速通道：

```
sensor_144/145  "Rotor speed 1/2"                      p50=9.79   彼此 r=1.0000
sensor_146/147  "Rotor speed gearbox main shaft 1/2"   p50=80     彼此 r=0.2073，會出現負值
```

## 5. 這個專案最重要的一課

**到目前為止最嚴重的缺陷，沒有一個會報錯。**

它們全部照常跑完、照常輸出漂亮的數字，只是數字是錯的。而且**全部都是拿真實
資料實跑才撞到的，沒有一個是讀程式碼讀出來的**。

清單（給後續協作者當檢查清單用）：

| 缺陷 | 後果 |
|---|---|
| FAR 算在故障案例上 | 把真陽性當誤報，讓最好的偵測器看起來最差（0.3102） |
| score CSV 表頭 `wind_speed` 重複 | DictReader 只留後者；感測器掉線的列風速被讀成空 → 落錯分箱 → **偏誤核心主張** |
| `[FARM:]` 前綴用子字串比對 | `A:` 命中三個風場（`farm` 裡有 a），兩個風場用錯誤風速欄分箱 |
| 把「可能發電量」當實測功率 | 最有資訊量的特徵失去偵測衰退的能力 |
| 850.0 故障碼進特徵向量 | 巨大 Mahalanobis 距離＝假警報 |
| `scorer_summary.json` 固定檔名 | 三風場寫同一目錄，Farm C 蓋掉 A 和 B |
| 單位檢查器用比例比較攝氏 | 三個假警報。**會叫錯狼的檢查器比沒有更糟**——它訓練人忽略它 |
| 診斷工具預設只讀 8/58 個檔案 | 印「from 8 case file(s)」卻不說總數，把一角當全貌 |
| `median_lead_days` 只在有偵測到的案例上取中位數 | 漏檢離開母體而非計為漏檢 → **漏掉越多困難案例分數越好看**。dtaci 的「提前 33.44 天」是 6 取 1 |
| lead time 無下界 | 故障發生**之前**的誤報被計為提前預警，而且報得越早收割越多 |

最後兩項合起來，讓一個評估器缺陷被誤判為方法缺陷，並以「主要限制條件」
呈報上去，**差一步就會導致動用已簽核參數去修一個量尺的錯**（見 6.1）。

**由此形成的工作準則**：

1. 每支工具都要有自己的行為測試。
2. 新測試要**反向驗證**——把修正還原，確認測試真的會失敗。只會 PASS 的測試是裝飾。
3. 檢查要能**兩個方向都失敗**。只往一邊失敗的檢查不是證據。
4. 取樣要說明涵蓋率。跨距取樣可能完整漏掉週期性異常（實際發生過：
   每 40 列注入、每 20 列取樣，完美錯開）。
5. 物理範圍、閘門門檻這類定義只能有**一份**。兩支工具對「什麼叫可能」意見不合，
   比其中一支寫錯更糟。
6. **任何要呈報為「方法限制」的負面結果，呈報前先在真值已知的合成資料上做一次
   歸因**，確認那個限制不是量尺造成的。`scripts/diagnose_earliness_gap.py`
   是這個流程的範例：先逐一重現被質疑的數字，再逐項排除候選解釋。
7. **統計量一律連同分母一起呈現。** 中位數、比率、平均，只要母體會隨方法變動，
   就必須把 n 印在旁邊。上表最後兩項都是分母被藏起來造成的。

### 8.1 文件命名規範（2026-08-15 新增，起因見下）

**問題**：多位協作者（Gemini Spark、Codex B、排程自動化研究助理，加上不只一個
同時執行的 session）各自遞增版本號，於是同一個版本號被不同人用在不同文件上。
截至 2026-08-15 已發生 **6 組撞號**：v1.7、v1.8、v2.2、v2.4 各兩份，
v3.0 三份，v3.9 兩份。最嚴重的一次是 v4.0 已存在後又出現一份 v3.9，
**最新的紀錄反而掛著最舊的版號**。

**根因**：版本號是一個需要全域協調的計數器。並行寫入時它必然碰撞——
這不是誰粗心，是編號方式本身不適用於多寫入者。

**規範**：日誌與進度文件標題一律採

```
<文件類型> v<版號> — <YYYY-MM-DD HHMM> — <作者>
例：風能運維論文協作開發日誌 v4.1 — 2026-08-15 2211 — 排程自動化研究助理
```

- **時間戳是真正的識別碼**，版號只是給人讀的順序提示。
  時間戳天然唯一，不需要任何人協調。
- 撞號時**不改動歷史文件的版號**（其他文件會引用它），
  只補上時間戳與作者以資區別。
- 新建文件前**先看資料夾裡最大的版號**再遞增；不確定就直接用時間戳。

**判斷「哪一份最新」時，一律看時間戳，不要看版號。**

> 更根本的解法是別再用 Drive 追狀態：**現況以本文件為準，日誌只記流水帳**。
> 本文件在版控裡，天然有唯一的歷史與衝突處理，不會有這個問題。
